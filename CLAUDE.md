## Tech Stack
- Python 3.12+ with FastAPI (all 5 services)
- Dapr 1.14+ (pub/sub, service invocation, state store, secrets)
- RabbitMQ 3.13 (via Dapr pub/sub component)
- PostgreSQL 16 (business records + outbox, and separately the Dapr state store)
- Zipkin (Dapr tracing, one end-to-end trace per request)
- NGINX gateway, React 19 SPA (Vite)
- Docker Compose (18 containers: 5 services + 5 Dapr sidecars + placement, postgres,
  rabbitmq, zipkin, gateway, ui, and 2 one-shot init containers)
- CI: GitHub Actions (ruff + mypy + unit/integration/UI tests + compose smoke test, then CD to GHCR)

## Project Structure
```
services/
  shared/           Pydantic models shared across all services (installed at Docker build time)
  ingestion/        Accept submissions, validate, publish submission.received
  agent/            LLM analysis: classify, extract, recommend, assign confidence
  router/           Deterministic gates (configured rules + ceiling + confidence) — zero AI,
                    the single source of truth; also the admin policy API and the reports
  payment/          Saga orchestrator: reserve → execute → confirm → compensate
  notification/     Event observer, HITL approver queue, status API
tests/
  unit/             Pure logic tests (no Docker, no network, no database)
  integration/      Against a real PostgreSQL; self-skip when it is unreachable
scripts/
  verify.py         D5 verification: the 4 journeys + the anti-cheese guards (npm run verify)
eval/
  harness.py        B1 eval harness over the labelled fixtures
dapr/
  config.yaml       Tracing configuration (wired into every sidecar with -config)
  components/       Dapr components (pubsub, statestore, secrets, subscriptions)
db/init/            PostgreSQL schema, applied on first boot
config/             Bootstrap policy + autonomy configuration
ui/                 React SPA — submission form, status view, approver queue
gateway/            NGINX reverse proxy + rate limiting
```

## Key Commands
```bash
# Start fresh (always use this — stale volumes cause issues)
docker compose down -v && docker compose up -d

# Wait for healthy (~60s), then verify all 4 journeys
python eval/harness.py

# Unit tests (no Docker needed)
pytest tests/unit/ -v

# Integration tests
pytest tests/integration/ -v

# Lint + type check
ruff check services/
mypy services/ --explicit-package-bases --ignore-missing-imports
```

## D5 Verification
```bash
# Run all 4 worked journeys (auto-approve, escalate-and-resume, duplicate, payment-failure)
python eval/harness.py

# Run a single journey
python eval/harness.py --journey A    # INV-1001: auto-approve
python eval/harness.py --journey B    # INV-1003: escalate-and-resume
python eval/harness.py --journey C    # INV-1007: duplicate detection
python eval/harness.py --journey D    # INV-1012: payment failure + compensation
```

## Skill Workflow

### Starting a new feature
1. Invoke brainstorming skill first — design before code
2. Write spec, get approval
3. Use writing-plans skill for implementation plan
4. Implement following the plan

### Writing code
- Router logic, decision engine, pure functions → use test-driven-development skill (test first)
- Dapr wiring, event handlers, pub/sub plumbing → implement first, then add tests
- Bugfixes → use systematic-debugging skill first, reproduce with a test before fixing

### Quality gates (before every commit)
```bash
ruff check services/                    # must pass
mypy services/ --explicit-package-bases --ignore-missing-imports  # must pass
pytest tests/unit/ -v                   # must pass
```
If integration-sensitive code changed, also: `pytest tests/integration/ -v`

### Before pushing
- All quality gates must pass locally (ruff, mypy, pytest)
- Review the diff — never blind-push
- Router changes: M12 proof tests must pass (`pytest tests/unit/test_router_decision.py -v`)

### Before merging (human step — Claude never merges)
- Use requesting-code-review skill
- All CI gates green
- PR approved by a human

## Commit Conventions

### Format
`<type>: <description>` (Conventional Commits)

### Types
`feat:` | `fix:` | `test:` | `refactor:` | `docs:` | `chore:`

### Size
- Small/single-concern → one tight commit
- Feature work → can bundle a coherent unit across services, but nothing massive
- Rule of thumb: if the commit message needs a bullet list of unrelated things, split it

## Git Workflow
- Claude can: create branches, write code, run quality gates, commit, push feature branches, open PRs
- Claude cannot: merge PRs, push to dev or main directly
- Branch naming: `feat/<description>` or `fix/<description>`
- Branch off `dev`, merge back via PR
- Review the diff before any push — never blind-approve

## What NOT to do
- Never push directly to `dev` or `main`
- Never commit `.env` files or secrets
- Never skip tests because "it's a simple change"
- Never suggest bypassing NetFree or using an unfiltered connection
- Never modify shared models (`services/shared/`) without checking all 5 service consumers
